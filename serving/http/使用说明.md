# HTTP Gateway 使用说明（当前实现）

本文档只描述当前 `serving/http` 目录对应的真实实现，不再沿用早期“HTTP 只做 StackFlow 转发”的旧边界定义。

## 1. 当前模块职责

`serving/http` 现在承担的是完整的 HTTP 接入层职责：

- TCP 连接级 HTTP 组包
- OpenAI 风格请求解析与错误码映射
- `/healthz`、`/v1/models`、admin status
- `POST /v1/chat/completions`
- `POST /v1/embeddings`
- `POST /v1/rerank`
- 流式 SSE 输出
- 与 `SessionManager`、`SessionExecutor`、`EngineExecutor`、`AgentExecutor` 衔接

它不直接做模型推理，但它已经不是“只把 HTTP 包翻成 StackFlow RPC”的薄适配层。

## 5. HTTP 组包模型

核心文件：

- `serving/http/NetworkHttpServer.cc`

当前实现要点：

- 每个连接维护独立缓存 `http_buffers_[conn]`
- `onMessage()` 只负责把新字节追加到缓存
- `handleHttpRequest()` 查找 `\r\n\r\n`
- 严格解析 `Content-Length`（POST 缺失时返回 `411 Length Required`）
- 拒绝 `Transfer-Encoding: chunked`
- body 没收齐时直接返回等待下一波 TCP 数据
- 收齐后构造 `HttpRequest` 并消费已处理缓存

这部分是当前 HTTP 稳定性的基础，负责解决 TCP 分包和粘包。

## 6. 路由与请求解析

### 6.1 路由

当前 `NetworkHttpServer` 做的路由分发包括：

- `OPTIONS` CORS 预检
- `GET /healthz`
- `GET /health`（兼容别名）
- `GET /v1/models`
- `GET /admin/models/status`
- `GET /admin/backends/status`
- `POST /v1/chat/completions`
- `POST /v1/embeddings`
- `POST /v1/rerank`

兼容/实验路由仍保留分发入口，但 agent/rag 专用路由默认在 `HttpGateway` 中返回 `404 experimental_api_disabled`。

流式优先读取 JSON body 的 `"stream": true`，query `?stream=true` 仅兼容兜底。

### 6.2 Chat 请求解析

核心文件：

- `serving/http/ChatRequestParser.cc`

当前会解析：

- `model`
- `messages`
- `session_id`
- `max_tokens`
- `inference_backend`
- `agent`
- `agent_mode`
- `max_steps`
- `tools`
- 各类采样参数

解析结果统一进入 `ServingContext`。其中 `agent*` 和 `rag` 字段只作为兼容扩展继续保留，不再驱动主线 API 设计。

当前对外 `agent_mode` 语义：

- `code_analysis`
  主推模式，也是默认值；优先仓库、本地文档、配置和运行时证据。

- `web_research`
  补充模式；仅在需要外部资料交叉验证时补充受控 `search_web / fetch_url`。

- `generic`
  保留内部实验用途，不作为公开 HTTP 模式；来自外部请求时会回退到 `code_analysis`，`/v1/agent/debug` 也不会把它作为公开可选项。

## 7. HttpGateway 当前真实职责

核心文件：

- `serving/http/HttpGateway.cc`

当前真实职责如下。

### 7.1 初始化服务内对象

`HttpGateway` 构造函数里会初始化：

- `ThreadPool`
- `EngineExecutor`
- `SessionExecutor`
- `SessionManager`
- `AgentExecutor`
- `RAGExecutor`
- `EmbeddingsService`
- `RerankService`

并为 agent 注入一个 `status_provider`，让 `get_server_status` 可以返回服务当前指标。

### 7.2 非流式路径

`HandleChatCompletion()` 当前流程：

1. 解析请求体
2. 构造 `ServingContext`
3. 申请治理 lease，执行全局 / 模型 / session 并发限制
4. 记录请求日志
5. 按 `http_request_timeout_ms` 设置请求 deadline
6. 通过 `SessionExecutor` 提交任务
7. 若 `agent=true`，执行 `AgentExecutor::Run`
8. 否则执行 `EngineExecutor::Execute`
9. `WaitFinishOrCancel()` 等待完成或连接断开
10. 根据 `finish_reason` 与 `error_message` 返回 JSON 或错误

### 7.3 流式路径

`HandleChatCompletionStream()` 当前流程：

1. 解析请求体
2. 申请治理 lease，执行全局 / 模型 / session 并发限制
3. 按 `http_request_timeout_ms` 设置请求 deadline
4. 创建 `HttpStreamSession`
5. 创建 `OpenAIStreamWriter`
6. 把 `ctx->on_chunk` 绑定到 writer
7. 通过 `SessionExecutor` 提交执行任务
8. engine 通过 `ctx->EmitDelta` 输出 chunk
9. 完成时输出 finish chunk 和 `[DONE]`

### 7.4 Session 更新策略

当前只在以下情况把 assistant 回答写回 session：

- `stop`
- `length`

对于：

- `cancelled`
- `error`

不会污染会话历史。

## 8. `/v1/models` 的当前语义

`GET /v1/models` 基于 `ModelRegistry::ListModelInfos()` 生成。

当前代码里：

- `model` 表示逻辑模型名，`inference_backend` 表示请求级推理后端选择
- `backends` 表示模型在配置里已声明的后端能力（模型级）
- `gateway_backends` 表示网关支持的请求级后端切换能力（路由级）
- 前端应允许在同一个逻辑模型上切换 `inference_backend`
- 当模型未显式声明 rpc 时，`inference_backend=rpc` 当前仍可走全局 stackflow fallback（弱配置语义）
- `*-remote` 仅保留兼容解析，不再建议写入主配置

## 9. 错误处理与状态码

当前常见状态码：

- `200` 正常
- `204` CORS 预检
- `400` 参数错误、废弃接口、非法请求
- `404` 路由不存在
- `405` 方法不允许
- `429` session queue 或 model queue 过载
- `500` 内部错误
- `501` 不支持的接口模式

错误体统一使用 OpenAI 风格：

```json
{
  "error": {
    "message": "...",
    "type": "...",
    "code": "..."
  }
}
```

## 10. finish_reason 与 SSE

当前 `serving/http` 已经可以正确透传以下 finish reason：

- `stop`
- `length`
- `cancelled`
- `error`

配套文件：

- `serving/http/OpenAIStreamWriter.cc`
- `serving/core/ServingContext.h`

最近修复后的行为：

- RPC / worker 链路若生成长度触顶，会回到 `length`
- SSE 结束 chunk 会携带正确 `finish_reason`
- HTTP 连接断开会通过 `cancelled` 传播到 `ServingContext`
- `http_request_timeout_ms` 命中时会统一返回 `request_timeout`

## 12. 配置项

HTTP 层直接或间接依赖的主要配置：

- `HTTP_PORT`
- `WORKER_THREADS`
- `DEFAULT_MODEL`
- `DEFAULT_MAX_TOKENS`
- `MAX_MODEL_QUEUE`
- `MAX_SESSION_PENDING`
- `MAX_QUEUE_WAIT_MS`
- `HTTP_REQUEST_TIMEOUT_MS`
- `MAX_CONCURRENT_REQUESTS`
- `MAX_MODEL_CONCURRENCY`
- `MAX_SESSION_CONCURRENCY`
- `CONFIG_PATH`
- `EXPERIMENTAL_AGENT_API_ENABLED`
- `EXPERIMENTAL_RAG_API_ENABLED`

此外，底层 engine 还会继续读取：

- `LLAMA_*`
- `STACKFLOW_*`
- Redis session 持久化相关配置

这些通常来自根目录 `config.json`，由 `http_main.cc` 读取并写入环境变量。

当前 `config.json` 中和治理直接对应的新增字段为：

- `http_request_timeout_ms`
  映射为 `HTTP_REQUEST_TIMEOUT_MS`，控制单个 HTTP 请求总超时；chat、embeddings、rerank 共用。
- `max_concurrent_requests`
  映射为 `MAX_CONCURRENT_REQUESTS`，限制网关整体并发中的请求数。
- `max_model_concurrency`
  映射为 `MAX_MODEL_CONCURRENCY`，限制同一逻辑模型的并发请求数。
- `max_session_concurrency`
  映射为 `MAX_SESSION_CONCURRENCY`，限制同一 `session_id` 的并发请求数。

## 14. 最后一句话

当前 `serving/http` 的正确定位是：

> 一个完整的 OpenAI 风格 HTTP/SSE 接入层，负责协议边界、请求解析、错误映射、session 编排入口和流式输出，而不是早期定义里的单纯 RPC 转发壳。

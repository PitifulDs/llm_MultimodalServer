# 智能指针的使用（unique_ptr / shared_ptr / weak_ptr）

本文档总结本仓库里智能指针的**真实使用方式**（按“生命周期/并发”来选型），方便代码评审与面试复述。

## 1. 选型原则（本项目的主规则）

1. **明确唯一所有权**：用 `std::unique_ptr`
2. **跨线程/异步共享生命周期**：用 `std::shared_ptr`
3. **后台线程/回调不应延长对象寿命**：用 `std::weak_ptr`
4. **用 RAII 表达“借用/租约”**：用 `std::shared_ptr<void>`（或专用 token 类型）承载析构回收

## 2. unique_ptr：明确 owner（组件组合）

典型位置：`HttpGateway` 构造时“组装服务内对象”。

- 文件：`serving/http/HttpGateway.cc`
- 形态：`HttpGateway` 成员里持有 `std::unique_ptr<SessionManager>`、`std::unique_ptr<ChatService>`、`std::unique_ptr<EmbeddingsService>` 等

原因：

- 这些对象的生命周期与 `HttpGateway` 一致
- 明确谁负责释放资源（避免 shared_ptr 的隐式共享导致难排查的泄漏/延长寿命）

## 3. shared_ptr：跨线程任务共享（ServingContext / Session / Response）

### 3.1 ServingContext：推理任务的共享载体

Chat 侧执行链路会跨线程、跨回调存活，所以 `ServingContext` 以 `std::shared_ptr` 贯穿：

- 提交：`SessionExecutor::Submit(std::shared_ptr<Session>, task)`
- 执行：`EngineExecutor::Execute(std::shared_ptr<ServingContext>)`
- SSE：lambda capture `ctx`，在 stream 生命周期内持续写 delta/finish

核心思想：

- **谁需要保证 ctx 活着，就持有 shared_ptr**
- ctx 内部用 `atomic(cancelled/finished)` + 条件变量协调等待/结束

### 3.2 Session：会话对象跨请求共享

`SessionManager` 返回的是 `std::shared_ptr<Session>`，用于：

- 多轮对话共享 history / KV cache
- `SessionExecutor` 以 session 为粒度做串行 drain

## 4. weak_ptr：后台 watchdog 不“绑架生命周期”

典型场景：超时 watchdog / 后台线程只应观察对象状态，而不是让对象永远不释放。

示例：

- 文件：`serving/http/HttpGatewayInternal.cc`
- `StartContextDeadlineWatchdog(const std::weak_ptr<ServingContext>&, ...)`

行为：

- watchdog 线程循环 `weak_ctx.lock()`，拿不到说明 ctx 已经释放，线程自然退出
- 避免“超时线程”把 ctx 强行延长，造成内存与会话无法回收

## 5. RAII 租约：用 shared_ptr<void> 表达“并发占用令牌”

本项目里并发治理用“租约 token”表达：只要 token 活着，就认为该请求占用了一份并发额度。

示例：

- 文件：`serving/http/HttpGateway.cc`
- `PlatformError HttpGateway::AcquireRequestLease(..., std::shared_ptr<void> &lease)`

实现方式：

- 在函数内部定义 `struct Lease { ~Lease(){ ReleaseRequestLease(...); } }`
- 返回 `lease = std::make_shared<Lease>()`

效果：

- 业务代码不需要在每个 return 分支手动释放
- 异常/提前返回也能自动回收（RAII）

> 如果后续要更强类型安全，建议把 `std::shared_ptr<void>` 替换成 `std::shared_ptr<RequestLease>`（专用类型），但当前写法在接口层已经足够表达语义。

## 6. 回调 capture 的注意事项（避免悬垂/循环引用）

### 6.1 避免捕获裸指针做跨线程回调

不要把局部对象地址或可能先析构的裸指针 capture 到线程池任务里；优先 capture `shared_ptr` 或拷贝必要数据。

### 6.2 处理“循环引用”

当 A 持有 B（shared_ptr），B 的回调又 capture A（shared_ptr）时会形成环，导致泄漏。

经验做法：

- 长生命周期对象（例如 `ServingContext`）由上层持有 shared_ptr
- 回调里如需引用上层对象，优先 capture `weak_ptr`，在回调里临时 `lock()`

### 6.3 handler 同步接口中的取消标记

Embeddings/Rerank 的同步 handler 使用：

- `request.cancelled = std::make_shared<std::atomic<bool>>(false)`
- watchdog 线程在客户端断连时 `cancelled->store(true)`

原因：

- `std::atomic<bool>` 本身不可复制；shared_ptr 让多个线程安全共享一个取消标志
- 生命周期由 handler 控制（离开 handler 即析构），避免泄漏

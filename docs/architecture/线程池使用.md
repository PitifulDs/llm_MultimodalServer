# 线程池的使用（ThreadPool / EventLoopThreadPool）

这份文档描述仓库里两类“线程池”的真实用法与边界：

- **网络 IO 线程池**（Reactor）：`network::EventLoopThreadPool`
- **业务执行线程池**（Serving）：`serving/core/ThreadPool`

目标是让你在读 `HttpGateway`、`SessionExecutor`、`EngineExecutor` 时能快速形成并发心智：**IO 不被推理阻塞**，同时对话与引擎状态具备可控顺序。

## 1. 两种线程池分别干什么

### 1.1 network::EventLoopThreadPool（IO 线程）

核心文件：

- `network/include/network/EventLoopThreadPool.h`
- `network/src/EventLoopThreadPool.cc`
- `network/src/TcpServer.cc`

职责：

- 运行 Reactor 事件循环（epoll/Channel）并处理 socket 读写回调
- 连接在多个 `EventLoop` 线程之间分配（通常 round-robin）

原则：

- **IO 线程只做轻量工作**：收包、组包、路由分发、回包
- **不在 IO 线程做推理/长耗时任务**（否则拖慢所有连接）

### 1.2 serving/core/ThreadPool（业务线程）

核心文件：

- `serving/core/ThreadPool.h`
- `serving/core/ThreadPool.cc`

职责：

- 承载 Serving 的“业务执行任务”，包括 session 串行 drain、模型队列 drain、以及推理调用
- 由 `HttpGateway` 持有并注入到 `SessionExecutor`、`EngineExecutor`

线程数来源：

- 环境变量 `WORKER_THREADS`（由 `serving/http/http_main.cc` 从 `config.json` 的 `worker_threads` 写入 `WORKER_THREADS`）
- 读取逻辑：`serving/http/HttpGatewayInternal.cc` 的 `GetWorkerThreads()`

## 2. ThreadPool 的行为与注意事项

### 2.1 Submit 的语义

`ThreadPool::Submit(std::function<void()>)`：

- 把 task 入队，唤醒一个 worker 执行
- task 执行时不持有 `ThreadPool` 内部锁

### 2.2 退出行为（重要）

`ThreadPool::~ThreadPool()` 会：

- 设置 `stop_=true`，唤醒 worker 并 join
- **不会保证队列中的任务被 drain 完**（stop 置位后 worker 可能直接退出）

因此它适用于“进程级服务退出”的场景；如果你需要“优雅停机 drain 全部任务”，需要额外的 shutdown 协议（当前实现不提供）。

## 3. Serving 的两级串行队列如何使用线程池

Serving 侧的并发模型可以概括为：

> `IO 线程 -> 业务线程池 -> 两级串行队列（session 串行 + model/backend 串行）`

### 3.1 SessionExecutor：按 session 串行

核心文件：

- `serving/core/SessionExecutor.h`
- `serving/core/SessionExecutor.cc`

做法：

- 每个 `Session` 维护 `pending` 队列与 `running` 标志
- 首个任务触发一次 `pool_.Submit(Drain(session))`
- `Drain()` 在同一线程里串行消费 `pending`，直到为空再把 `running=false`

背压：

- `MAX_SESSION_PENDING` 控制单 session 的队列上限（满了直接拒绝）

典型用途：

- chat：同一 `session_id` 的多轮请求严格串行，避免历史/上下文并发写导致污染

### 3.2 EngineExecutor：按 capability + model + backend 串行

核心文件：

- `serving/core/EngineExecutor.h`
- `serving/core/EngineExecutor.cc`

route key：

- `capability || model || resolved_backend`

做法：

- 每个 route key 维护一个 `ModelQueue`（内部 `tasks` + `running`）
- 首个任务触发一次 `pool_.Submit(RunModelQueue(route_key, mq))`
- `RunModelQueue()` 串行消费队列，确保同一路由 key 的引擎调用顺序可控

背压：

- `MAX_MODEL_QUEUE` 控制队列长度（满了直接 `queue_full`）
- `MAX_QUEUE_WAIT_MS` 控制排队等待时间（超过则 `queue_timeout`）

典型用途：

- chat：避免同一模型/同一后端上的推理状态竞争，并避免无限排队造成尾延迟扩散

## 4. Handler 侧的“同步接口”怎么用线程池

当前 `embeddings` 与 `rerank` 的 handler 是**同步执行**（不会提交到 `SessionExecutor/EngineExecutor` 的队列）：

- `serving/http/EmbeddingsHandler.cc`
- `serving/http/RerankHandler.cc`

它们仍会使用统一治理能力：

- `HttpGateway::AcquireRequestLease()`（全局/模型/会话并发限制）
- `StartSyncCancelWatchdog()`（客户端断连时取消）
- `HTTP_REQUEST_TIMEOUT_MS`（写入 deadline，service 内部按治理口径映射 timeout/cancel/error）

如果后续要把 embeddings/rerank 也改成异步队列化，建议复用 `EngineExecutor` 的 route key（至少按 capability+model+backend 隔离），并补齐对应的 metrics 口径。

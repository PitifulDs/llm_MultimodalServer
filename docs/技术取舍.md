# 架构取舍（Trade-offs）

## 1. 本地推理 vs 远程推理

| 维度 | 本地 llama | 远程 stackflow |
|---|---|---|
| 延迟 | 更低（无网络 hop） | 更高（多一跳网络+调度） |
| 吞吐扩展 | 受单机资源限制 | 可横向扩展 worker |
| 部署复杂度 | 低 | 高（unit-manager + worker + 通信链路） |
| 稳定性 | 相对稳定 | 依赖远程链路和会话状态管理 |
| 适用场景 | 单机 demo / 开发测试 | 多实例服务化 / 解耦部署 |

结论：
- 追求简单和稳定，优先本地 `llama`。
- 追求扩展性和资源解耦，使用 `stackflow`。

## 2. 非流式 vs 流式

| 维度 | 非流式 | 流式（SSE） |
|---|---|---|
| 体验 | 等全部完成后返回 | 首 token 快，交互更自然 |
| 实现复杂度 | 低 | 高（分块、结束帧、断连处理） |
| 前端适配 | 简单 | 需处理 chunk 和 `[DONE]` |

结论：
- ToB/工具链常用非流式。
- 面向交互体验优先流式。

## 3. work_id 复用 vs 每次新建

| 方案 | 优点 | 风险 |
|---|---|---|
| 复用 | 减少 setup 成本，提升吞吐 | 并发冲突、状态串扰 |
| 每次新建 | 状态清晰、隔离强 | 额外 setup 开销 |

结论：
- 默认复用 + 串行保护是折中。
- 问题定位阶段可先关闭复用保障正确性。
